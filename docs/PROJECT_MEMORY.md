SpectrumOS2 is a clean version-2 rewrite of SpectrumOS. It aims to turn a clean Arch installation into a minimal, cohesive, recoverable Wayland system for gaming and professional development through packages, configuration, services, migrations, and documented installation steps.

The desktop must remain simple and integrated. SpectrumOS2 should feel like one coherent system rather than a collection of independently configured applications. Shared semantic colors, spacing, interaction patterns, selectors, state handling, and rollback behavior should flow through the central Spectrum theme generation pipeline.

The legacy repository at `/home/gibranlp/SpectrumOS` is read-only reference material. All new work belongs in `/home/gibranlp/SpectrumOS2`.

## Decisions and conventions

- Use pacman for official Arch packages and paru only for AUR packages. Never introduce yay.
- Never perform partial Arch upgrades. Update design must operate as a coherent transaction.
- Package distro defaults under `/usr/share/spectrumos`; use `/etc/spectrumos` for administrator policy; keep user overrides under XDG paths; generated state must be separate.
- Do not overwrite an existing `~/.config` tree during installation.
- Prefer the simplest design that fully satisfies the requirement. Keep one clear owner for each behavior and avoid parallel mechanisms, extra modes, or abstraction without a demonstrated need.
- Default interactive shell is zsh with a pinned Oh My Zsh installation, a package-owned Spectrum Powerline prompt, the legacy SpectrumOS plugin set, and the official Arch `thefuck` package. The prompt replaces Agnoster's fixed Git colors with wallpaper-derived Spectrum terminal accents and retains semantic red only for actual failures. Framework self-updates are disabled; SpectrumOS controls revision changes. Personal/work fragments remain optional and separate.
- Substantial future `spectrum` CLI logic should be Rust; small, bounded bootstrap operations may remain shell.
- Hyprland is the v0.1 compositor. MangoWM and launcher replacements remain evaluations, not migrations.
- Adaptive theming is retained as an architecture, not as a direct copy of the legacy pywal scripts.
- Theme extractors and application renderers are separate. Extractors output the Spectrum semantic palette schema; complete rendered generations activate through one atomic `current` symlink replacement.
- Btrfs is the preferred recoverability baseline, but hardware/filesystem profiles must remain explicit rather than assumed.
- Hardware support is profile-driven; AMD, Intel, NVIDIA, laptop, desktop, and VM choices must not be merged into one unconditional manifest.
- Communicate with the user in English. Code comments are reserved for important functions or non-obvious behavior and must use natural, balanced Mexican Spanish. Documentation, identifiers, user-facing text, and commit messages remain in English. Required technical directives and third-party/generated text retain their mandated format.

See `docs/decisions/` for rationale.
